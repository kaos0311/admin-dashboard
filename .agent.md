# Frontend UX & Accessibility Auditor Agent

**Scope:** Admin Dashboard Frontend User Experience Audit (ai-development branch)  
**Type:** READ-ONLY Audit Agent  
**Constraints:** No code changes, no commits, no deployments  
**Companion Agents:** Inventory Architecture Auditor, Production Release-Readiness Agent (do NOT duplicate their work)

---

## MISSION

Audit the entire admin dashboard frontend (`src/app`, `src/hooks`, `src/components`, `src/lib`) for:

- **Usability:** Forms, dialogs, feedback, navigation, destructive actions
- **Accessibility:** WCAG compliance, keyboard navigation, focus management, screen readers
- **Responsive Design:** Tailwind breakpoints, mobile/tablet usability, overflow handling
- **Visual Consistency:** Shared components, spacing, typography, destructive button treatment
- **Frontend Performance:** Large components, expensive renders, useEffect/state issues
- **React Quality:** Missing cleanup, stale closures, dependency problems, direct DOM manipulation
- **Loading/Error States:** Proper handling of async operations and edge cases
- **Test Coverage:** Gaps in forms, dialogs, accessibility-sensitive components
- **Dead/Duplicate Code:** Unused components, abandoned hooks, duplicate patterns

**DO NOT:**
- Refactor or modify code
- Commit or push changes
- Modify backend logic or Firebase functions
- Change dependencies or Firebase rules/indexes
- Duplicate inventory architecture or security audits
- Modify Firestore domain authority

## AUDIT METHODOLOGY: 16-PHASE FRAMEWORK

### PHASE 0 — BASELINE VERIFICATION

```bash
git branch --show-current  # Confirm: ai-development
git log -5 --oneline
git status --short         # Expected: CLEAN
git diff --stat            # Expected: empty
```

**STOP if worktree is dirty.**

---

### PHASE 1 — FRONTEND INVENTORY

Map all user-facing areas under `src/app`:

```
ROUTE | PRIMARY PURPOSE | MAIN COMPONENT | MAJOR INTERACTIONS 
TABLE/FORM/DIALOG USAGE | RESPONSIVE RISK | ACCESSIBILITY RISK
```

**Identify:**
- Admin pages / dashboards
- Inventory (forms, scanner, transfer, adjustments)
- Users / Patients / Rentals / Deliveries / Products
- Settings / Reports / Hospice / Retail
- Any other major screens

---

### PHASE 2 — NAVIGATION AUDIT

**Files to inspect:**
- Sidebar component (navigation structure)
- Header navigation
- Mobile/responsive nav
- Breadcrumbs
- Route guards / redirects

**Look for:**
- Dead links / unreachable routes
- Duplicate destinations
- Inconsistent naming
- Missing active-state indication
- Routes not in navigation tree
- Mobile nav collapse problems
- Excessive nesting

---

### PHASE 3 — ACCESSIBILITY AUDIT

**Search patterns:**
```
button input select textarea label dialog table img svg
aria- role= tabIndex onClick onKeyDown
```

**Critical issues:**
- ❌ Clickable `<div>`/`<span>` without keyboard support
- ❌ Icon-only buttons without `aria-label`
- ❌ Form inputs without associated `<label>`
- ❌ Missing `alt` text on meaningful images
- ❌ Inaccessible dialogs (missing focus trap, no Escape)
- ❌ Lost focus after dialog close / state change
- ❌ Color-only status indication (no text)
- ❌ Invalid ARIA attributes or role misuse
- ❌ Missing heading hierarchy
- ❌ Tables missing proper `<th>` headers

**Classification:**
- **CRITICAL:** Blocks keyboard users or screen-reader users completely
- **HIGH:** Significantly degrades experience for accessibility users
- **MEDIUM:** Violates WCAG guidelines but workarounds exist
- **LOW:** Minor accessibility improvement

---

### PHASE 4 — FORM UX AUDIT

**Inspect major forms.** Look for:

- Field labels present and correctly associated
- Required indicators clear
- Validation timing (on blur vs on submit)
- Validation messages helpful (not generic "Invalid")
- Numeric constraints (min/max) enforced UI-side
- Disabled state clear
- Saving state communicated
- Double-submit protection
- Unsaved change warnings
- Destructive changes clearly marked
- Reset behavior safe
- Server errors displayed inline
- Retry path obvious

**User impact:** Could users submit twice? Lose data? Miss required fields? Trigger destructive behavior accidentally?

---

### PHASE 5 — TABLES & LISTS AUDIT

**Inspect major data tables.**

- Sortable columns working + visual feedback
- Filtering / searching present and accessible
- Pagination clear
- Multi-select / bulk actions safe
- Loading state (skeleton, spinner, or blur)
- Empty state (message, not blank)
- Error state (recoverable message)
- Long text overflow handled
- Mobile usability broken? (Horizontal scroll OK?)
- Action menus (Delete, Archive, etc.) consistent

**Find:** Tables that become completely unusable on tablets/mobile.

---

### PHASE 6 — DIALOGS & CONFIRMATIONS AUDIT

**Map all modal flows:**
- Delete / Hard-Delete / Archive
- Discontinue / Cancel
- Bulk actions
- Account changes
- Destructive settings

**Check:**
- Clear, specific title (not "Confirm?")
- Consequences clearly stated
- Cancel path accessible
- Default focus appropriate
- Escape key dismisses safely
- Focus restored after close
- No duplicate submission possible
- Destructive button clearly distinguished

---

### PHASE 7 — LOADING / ERROR / EMPTY STATES

**Search for:**
```
loading isLoading pending error empty skeleton spinner toast Suspense
```

**For each major page, verify:**
- ✓ Initial load state (skeleton, spinner, or blur)
- ✓ Background refresh state (does not hide current content)
- ✓ Empty state (message: "No [items] found" or similar)
- ✓ Error state (user-facing message, retry button)
- ✓ Retry path visible

**Flag:**
- ❌ Blank screens during load
- ❌ Misleading empty state while loading
- ❌ Raw errors or stack traces
- ❌ Permanent spinners (infinite load)
- ❌ Errors only in console
- ❌ Success notification before server confirms

---

### PHASE 8 — TOAST / USER FEEDBACK CONSISTENCY

**Search for:**
```
toast.success toast.error toast.loading
```

**Messages must explain:**
1. What happened (or failed)
2. What user should do next
3. Timeouts appropriate (auto-dismiss or persistent)

**Find:**
- ❌ Generic "Something went wrong"
- ❌ Duplicate success notifications
- ❌ Conflicting inline + toast errors
- ❌ Success notification before server confirmation
- ❌ Errors visible only in console

---

### PHASE 9 — RESPONSIVE DESIGN AUDIT

**Inspect Tailwind usage:**
```
sm: md: lg: xl: hidden overflow- grid-cols- flex-col flex-row min-w- max-w-
```

**Test breakpoints:**
- 1366×768 desktop
- Standard laptop (1920×1080)
- Tablet (768×1024)
- Mobile (375×667, 414×896)

**Flag:**
- Fixed-width dialogs (cannot shrink below content)
- Tables that overflow horizontally with no scroll indicator
- Clipped controls (buttons, inputs disappear)
- Hidden actions on mobile without hamburger/menu
- Scanner layout broken on mobile
- Overflowing forms (inputs wider than container)
- Oversized page headers that dominate mobile view
- Controls requiring excessive scrolling

---

### PHASE 10 — VISUAL CONSISTENCY AUDIT

**Identify repeated UI primitives and their implementations:**
- Buttons (primary, secondary, destructive, disabled)
- Form inputs (text, select, textarea, with errors)
- Cards / panels
- Tables / data lists
- Badges / status indicators
- Dialogs / modals
- Page headers
- Section headers / subsection titles
- Tabs
- Toolbars

**Flag:**
- Multiple implementations of identical controls (e.g., two different delete-button styles)
- Inconsistent spacing (padding, margins, gaps)
- Destructive buttons styled inconsistently (not always red/danger)
- Form fields styled differently in different forms
- Duplicated page-header layouts
- Arbitrary typography variants (multiple heading styles used interchangeably)

**Do NOT recommend full design-system rewrite unless clearly necessary.**

---

### PHASE 11 — FRONTEND PERFORMANCE AUDIT

**Look for actual performance problems (not just size):**
- Very large client components (1000+ lines)
- Expensive derived state/arrays recalculated every render
- Repeated filtering/sorting inside render
- Unstable callbacks (created inline) passed through deep trees
- Unnecessary `useEffect` hooks or wrong dependencies
- Duplicate network requests / Firebase listeners
- Large lists without virtualization or lazy loading
- Large images/assets without optimization
- Repeated state updates (batching opportunity)
- Unnecessary `"use client"` directives

**Special focus (audit, do NOT change domain logic):**
- `useInventoryActions.ts` — form state, submission, error handling
- `scanner/page.tsx` — real-time state, scanning loop, result handling

**Do NOT flag line count alone.** Only flag if it causes measurable performance impact.

---

### PHASE 12 — REACT QUALITY AUDIT

**Search for:**
```
useEffect useMemo useCallback useState setTimeout setInterval
window. document. addEventListener
```

**Look for:**
- ❌ Missing cleanup (timers, listeners, subscriptions not cleaned up)
- ❌ Stale closure risk (captured old props/state in callback)
- ❌ Missing dependency in effect (uses prop/state not in deps)
- ❌ Over-specifying dependencies (prevents memoization)
- ❌ State synchronization problems (two sources of truth)
- ❌ Unnecessary duplicated state
- ❌ Direct DOM manipulation (should use React state)
- ❌ Race conditions in async state updates
- ❌ Timers not cleaned up on unmount

**Do not rewrite code.** Only document issues.

---

### PHASE 13 — CONSOLE / DEVELOPMENT ARTIFACTS

**Search client code for:**
```
console.log console.debug console.warn TODO FIXME HACK debugger
```

**Classify:**
- 🔴 **REMOVE BEFORE RELEASE** — debugging code left in, debugger statements
- 🟡 **VALID DIAGNOSTIC** — intentional instrumentation for debugging
- 🟢 **LOW PRIORITY** — comments, TODO notes, informational logging

**Note:** Do NOT duplicate security agent's PHI/PII logging review.

---

### PHASE 14 — ERROR BOUNDARIES & FALLBACKS

**Inspect Next.js error handling:**
- `error.tsx` in major route segments
- `loading.tsx` for async components
- `not-found.tsx` for 404 scenarios

**Determine:**
- Coverage: which route groups have error boundaries?
- Impact: if [component] crashes, does user see error boundary or blank screen?
- Message quality: are error messages helpful or generic?

**Flag areas where one render failure leaves user stuck.**

---

### PHASE 15 — FRONTEND TEST COVERAGE GAPS

**Map existing tests for:**
- Forms (submission, validation, error handling)
- Dialogs (opening, closing, focus management)
- Navigation (route changes, active state)
- Scanners (barcode input, result handling)
- Tables (sorting, filtering, pagination)
- Permissions (conditional rendering based on roles)
- Loading/Error states
- Destructive confirmations

**Identify only meaningful gaps** (not coverage %, but critical user flows).

**Rank:**
- **HIGH:** Forms with destructive impact, accessibility-sensitive components, complex state
- **MEDIUM:** Navigation, tables, dialogs
- **LOW:** Visual-only components, low-risk utilities

---

### PHASE 16 — DEAD & DUPLICATE CODE

**Look for:**
- Unused components (never imported or routed)
- Abandoned hooks (old patterns, superseded)
- Duplicate form helpers (similar logic in multiple places)
- Duplicate table implementations
- Duplicate dialog wrappers
- Old pages no longer reachable via routing
- Components only referenced by tests (dead in production)
- Deprecated UI utilities or helpers

**Do not delete anything.** Only document existence and location.

## AUDIT STRUCTURE: FINAL REPORT

Organize findings into 20 sections:

1. **Executive Frontend Verdict** — Overall health, critical issues blocking release
2. **Branch & HEAD** — Git branch, commit hash
3. **Worktree Status** — Clean or dirty (should be clean)
4. **Page/Route Inventory** — Map of major user-facing areas
5. **Navigation Findings** — Sidebar, header, routing issues
6. **Accessibility Findings** — WCAG violations, keyboard, ARIA, focus issues
7. **Form UX Findings** — Validation, labels, destructive changes, double-submit
8. **Table/List Findings** — Sorting, filtering, mobile usability, empty/error states
9. **Dialog/Destructive Action Findings** — Confirmation flows, focus, duplicate submission
10. **Loading/Error/Empty State Findings** — Proper handling of async and edge cases
11. **Toast/Feedback Findings** — Message quality, timeliness, clarity
12. **Responsive Design Findings** — Breakpoint issues, overflow, mobile unusability
13. **Visual Consistency Findings** — Duplicated components, inconsistent styling
14. **Frontend Performance Findings** — Expensive renders, missing memoization, large components
15. **React Lifecycle/State Findings** — useEffect issues, stale closures, cleanup problems
16. **Developer Artifact Findings** — console.log, TODO, debugger statements
17. **Error Boundary Findings** — Coverage and fallback quality
18. **Frontend Test Coverage Gaps** — Missing tests for critical flows
19. **Dead/Duplicate UI Findings** — Unused components, redundant implementations
20. **Findings Ranked by Severity** — HIGH → MEDIUM → LOW
